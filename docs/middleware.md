# AudioLib 開発コンテキスト(claude.ai での相談の引き継ぎ)

## プロジェクト概要
- 自作 DirectX12 ゲームエンジンで使用するオーディオライブラリ「AudioLib」を開発中
- ただし設計思想として特定エンジン非依存を掲げる: 他のソフト・エンジンにも
  組み込めることがライブラリ/ミドルウェアの務めという考え。
  DX12 エンジンは「最初の統合先」であり、AudioLib 本体はエンジンに属さない
- 目標: ゲームオーディオミドルウェア(Wwise/FMOD/CRI ADX 的なもの)として
  就活ポートフォリオでアピールできる水準にすること
- 開発者はアプリプログラマ志望(描画エンジン開発経験あり)。DSP 専門ではなく、
  ツール・ワークフロー・API 設計・エンジン統合を強みとして打ち出す方針

## 設計原則(エンジン非依存の担保)
- Core は描画 API・ウィンドウシステム・特定エンジンに依存しない
  (依存は miniaudio と標準ライブラリ程度に限定)
- エンジンごとの統合コード(リスナー同期、エディタ組み込み等)は
  Core と分離した薄いバインディング層として実装
- 公開ヘッダに miniaudio の型を漏らさない(pImpl 等)、ハンドルベース API
- ImGui デバッグパネルは Core に ImGui 依存を入れない形で分離
  (統計取得 API を Core に置き、描画はオプショナルモジュール or 統合側)
  
## 現在の実装状況(相談時点)
- miniaudio のラップによる基本プレイヤー機能(再生など)
- Mixer 上に Track を作成(未指定時は Master)し、Track 単位で再生できる構造

## 相談で合意した方針
1. VST/CLAP ホスト化は当初構想していたが、優先度を下げた
   - ランタイムにプラグインを挿すのは実務では非現実的(コンソール非対応、ライセンス、負荷、クラッシュ耐性)
   - 挿すとしても将来のスタンドアロンエディタ側のみ。ランタイムへはベイク(WAV 書き出し)で反映する Wwise 的整理
   - DSP 学習目的なら「ホストを作る」より「プラグイン(エフェクト)を作る」方が効果的で、
     それは AudioLib の自前 Track インサートエフェクトとして実装すれば成果物に直結する
2. 将来構想としての層分け(実装は後、面接では構想として語る):
   - AudioLib Core(ランタイム、プラグイン依存ゼロ、リアルタイム安全)
   - Editor Core(データモデル、シリアライズ、Undo/Redo、エディタ⇔ランタイム通信。内蔵/スタンドアロン共用)
   - 内蔵 ImGui エディタ(エンジン統合、ホットリロード用)
   - スタンドアロン DAW ライクエディタ(将来。CLAP ホストはここだけ)

## 「最低限ミドルウェアと名乗れる」ための実装スコープ(優先順)
1. イベントシステム: JSON でイベント定義(ファイル、Track 割当、音量/ピッチのランダム幅)→ Play("event名") で発火。データとコードの分離
2. ボイス管理: 同時発音上限、優先度によるボイススチール(フェードアウト付き解放)
3. オーディオスレッドの安全化: API → コマンドキュー(ロックフリー or 軽量ロック)→ オーディオスレッドで消費。コールバック内での new/lock/file IO 禁止
4. RTPC 最小版: float パラメータで Track ボリュームがカーブ追従(1 本でよい)
5. 自前エフェクト 2 つ: バイクアッド EQ(LPF/HPF)+ ディレイかリバーブを Track インサートに
6. ImGui デバッグパネル: 発音中ボイス一覧、Track メーター(ピーク/RMS)

## 面接で語れるべき理解(チェックリスト)
- オーディオスレッドでロック/アロケーションが禁止な理由(コールバック締め切りとグリッチ)
- 再生指示が音になるまでのデータフロー(自分のコマンドキュー設計を図解できる)
- ボイススチール時にノイズを出さない方法
- バッファサイズとレイテンシの関係
- Wwise/FMOD が解決している課題と自作との共通点・差分
